# 导入 PureRef 图片

从当前画布的添加菜单选择「导入 PureRef 图片」，或把一个 `.pur` 文件拖到当前画布。程序先在本机解析并显示缩略图、独立图片数量、合并重复次数与跳过的外链数量。确认导入后，所有图片在本机从暂存文件逐张复制到当前项目，再统一加入画布并确认保存。完成的节点与普通图片素材相同，可继续连接电子主美、图生图或图片处理节点。

## 支持范围

- 读取 PureRef 容器版本 **2.1**、SQLite schema **200101** 中，被场景图片实例引用的内嵌资源（`source_type=1`）。本机 PureRef 2.0.3 与 2.1.3 保存的合成文件已验证此容器与 schema；应用版本号和容器版本号并不相同，不能据此保证任意 2.x 文件都支持。
- 支持可完整解码的静态 PNG、JPEG 和 WebP，保留 `.pur` 中的编码字节和透明通道，不重新压缩。动画和其他编码暂不支持。保存优化可能使 PureRef 内嵌内容不同于最初拖入 PureRef 的源文件；导入器只能提取实际内嵌内容。
- 同一资源的重复实例及编码字节完全相同的资源只创建一个节点，并显示合并次数。未被场景引用的旧资源不会导入。
- 图片按网格追加到现有节点右侧。**不恢复原布局、旋转、缩放、分组、裁剪、绘画、文字或注释**；导入原内嵌图，不是画板截图。
- 外链与非内嵌资源按实例计数并跳过，不访问其中的本地路径或网址。不会导入文件路径、原始文件名或场景元数据；图片使用 `PureRef-001.png` 等生成名称。只有外链、没有可导入图片时明确报错。
- PureRef 1.x 使用独立格式，当前明确不支持；不匹配的容器／schema、损坏文件和校验和失败都会停止，不生成空图片节点。

## 上限与错误恢复

文件最多 **8 GiB**、图片资源表最多 **2048** 项、场景图片实例最多 **16384** 项；每张编码图片最多 **128 MiB**、单边最多 16384 像素、单图最多 64 × 1024² 像素。导入后现有节点与新图片节点合计不能超过 **4096**；在复制图片前和加入画布前都检查。大批量导入只定位第一行图片，其他节点随视口进入后加载项目缩略图。

浏览器按 4 MiB 分块上传到当前用户私有的本机暂存目录，上传与解析都有进度和取消入口。默认暂存位于工作台 runtime 的 `pureref-import`，可由服务进程环境变量 `H3_PUREREF_CACHE_DIR` 指定（仅允许新的或空的专用目录，已有目录必须具有有效缓存标记；禁止位于程序、项目或已登记外部项目内）。最多保留两个会话、同时解析一个文件，静置一小时后回收；正常关闭和下次开始导入时会清理可验证归属的残留，不会清理未知目录。

暂存预检需要源文件两倍加 512 MiB；复制前还要求项目磁盘容纳全部待复制图片、单张临时文件与 512 MiB。若在同一磁盘，完整导入峰值可能接近源文件三倍加余量。磁盘不足时停止并保留现有画布，不可把「两倍暂存」理解为总空间需求。

解析和预览不会向项目写入图片。取消会终止独立解析进程，或等待当前复制及 receipt 核对完成后停止，不再复制后续资源。取消和复制失败都不会添加半批节点。此前成功保存的不可变素材可能暂时留在项目资产目录，不会删除去重共享素材。服务端复制复用 `store.put_asset` 与 `If-Match`，页面沿现有媒体写入队列更新 revision。若复制已完成但响应丢失，只有限重试同一资源、同一原始 `If-Match` 请求，由会话 receipt 核对；不刷新未知 revision。无法确认时保留错误供处理。


全部节点加入后若最终保存响应失败，界面明确提示「保存尚未确认」，不会自动重复导入。请保留页面，用项目菜单重试保存，确认已有节点后再进行其他操作。导入期间项目切换和底层可写状态受保护；原 `.pur` 与现有画布节点不修改。

## 实现与验证边界

解析在本机完成，不需要云端模型或 API Key。源 `.pur` 不会修改；只有本机暂存副本在校验后原位恢复 SQLite 前缀。源文件和图片 BLOB 都不整体读入内存：物理 MD5、SQLite `blobopen`、原编码提取与项目复制均按至多 1 MiB 处理。预览接口只返回 160px 衍生图，页面只取前 12 张，通过 capability 请求头获取并及时释放 blob URL；capability 只在创建响应与后续请求头传递并保留在内存，资源描述、项目和 URL 中不含 capability、源路径或原图 Base64。

SQLite 以磁盘 `mode=ro&immutable=1` 打开，采用 query-only、trusted_schema OFF、禁扩展、禁附加数据库、固定字段 SELECT、普通表与整数主键检查；显式验证 rowid 与资源 id 对应，且每个图片实例必须存在基本 item。只读取必要图片字段，不读取源路径、URL、笔记或 HTML。容器 MD5 仅用于发现损坏，不代表文件可信。

每张图片经实际像素解码和尺寸检查，再保留原编码。Pillow 仍可能为单张图片分配完整像素或压缩内容（尤其 WebP），因此单图受独立上限保护；解析在可终止的子进程运行，768 MiB RSS 上限、30 分钟时间预算，父服务退出后也会停止。不是浏览器或主服务整包解析。旧 `pureref_import.py` 小字节接口只保留用于独立小型合成回归；旧 `/api/pureref/inspect` 不再提供运行入口。


实现依据公开格式事实独立编写，没有复制第三方解析实现或数据库 schema。参考：[PureRef 官方自动化](https://www.pureref.com/handbook/2.0/automation/)、[公开容器事实](https://github.com/Vacyyyy/pur-2-file-format/blob/main/FORMAT.md)。后者研究的是应用 2.1.3，本项目另用本机 2.0.3 和 2.1.3 原生合成文件验证了 PNG、JPEG、透明度与重复资源；这些含本机合成路径的原生文件不随源码发布。

回归使用新生成的合成容器，以及可选本地原生合成样本，覆盖版本、损坏、校验和、类型、外链、孤立资源、解码、上限、取消、切换、上传失败、保存未确认和真实后端导入／重开。没有读取用户画板或运行真实付费推理。


可选大文件测试（使用自有合成文件；不默认纳入普通测试）：设置 `H3_TEST_PYTHON`、`PUREREF_LARGE_FIXTURE`、`PUREREF_EXPECTED`（包含 expected sha256/bytes 的 JSON）、`PUREREF_EVIDENCE` 后运行 `node test-pureref-large-perf.mjs`。它使用独立后端与项目、浏览器 `setInputFiles(path)`、真实分块上传、分页与 12 张预览、顺序复制与原子发布、重开和取消，并记录各进程 RSS。容量结构文件中的惰性填充必须与真实图片编码字节分别报告，不得混称真实图片负载。
