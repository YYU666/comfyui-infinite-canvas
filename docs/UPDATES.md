# Release 检查与一键安全升级

## 用户操作

1. 保持网络可用，正常启动 Refmuse 本地工作台。默认在启动后及每 4 小时检查 `YYU666/comfyui-infinite-canvas` 的最新正式 GitHub Release。页面隐藏或离线时暂停；返回页面或恢复联网后补做已到期检查。正在检查、查看更新窗口或升级时不会重叠检查。
2. 自动发现新版会显示小提示，点击“查看更新”再阅读版本号和 Release notes。关闭提示或选择“稍后”后，同版本不再自动提醒；仍可在“设置 → 程序更新”手动检查。关闭“自动检查 GitHub Release”立即生效，手动检查仍可用。离线、限流或没有新版时不会自动弹出错误。
3. 升级前保存当前项目并返回项目启动页，等待生成和排队任务结束。活动任务、打开的项目、Git 跟踪文件的本地修改、磁盘空间不足都会阻止升级。
4. 点击“立即升级”后不要关闭电脑。程序下载并校验更新包，在独立目录安装 Node 依赖和构建画布，然后由工作台外部恢复程序备份、替换、安装锁定的 Python 依赖并重启。页面健康检查到目标版本后自动刷新。

这是一套“自动检查＋用户确认＋自动安装”机制，不会未经确认静默升级。

## 保留与替换边界

更新包只含 Git 跟踪的工作台源码和文档；构建阶段生成独立 `dist/` 与 `node_modules/`。更新不会替换或清空：

- ComfyUI 本体和第三方节点；
- 模型、LoRA 和外置模型目录；
- 项目根目录、引用素材、生成结果和导出；
- `%LOCALAPPDATA%\H3Workbench\config.json`、系统密钥库和其他用户设置；
- 工作台目录内不属于更新清单的本地未跟踪文件。

Git 安装会在下载前和重启前两次检查代码。更新器造成的差异仅在文件与本安装目录的已安装清单哈希完全一致时允许继续；用户修改或暂存的改动仍会阻止升级。已安装清单按安装目录隔离并验证归属；另一目录或旧版共用的清单不会用于删除本目录文件。首次升级没有历史文件清单时，不删除无法确认归属的旧文件；后续升级只清理上一版清单登记、且新版已删除的程序文件。旧文件仍会保留在本次更新备份中。

## 包完整性与故障恢复

- Release 必须同时提供 `refmuse-update-<tag>.zip` 和同名 `.zip.sha256`。
- `refmuse-update-*` 只用于覆盖更新已经安装好的工作台，目标机器仍会在本地执行 `npm ci` 和 `npm run build`。它不是空目录安装包，也不包含 `dist/`。引擎隔离目录请安装 `refmuse-portable-*`，说明见 `docs/OFFICIAL_ISOLATED_LAUNCH.md`。
- 后端只从固定官方仓库读取 Release，下载地址必须为 GitHub HTTPS；客户端只能提交刚确认的 `tag`，不能提交下载 URL。
- 下载包限制为 128 MiB、2500 个文件、解压后 256 MiB。ZIP 路径逃逸、绝对路径、符号链接、重复清单、额外文件、缺失文件、错误版本和错误 SHA256 均拒绝。
- `package.json`、`workbench_lifecycle.APP_VERSION` 和 Release 标签必须一致。校验只解析文本和 AST，不执行下载包中的安装脚本。
- 工作台进程退出后才替换文件。更新重启会在有限时间内结束画布自己的进程，不会结束 ComfyUI。若 120 秒内旧进程仍不退出，助手把状态写成 `error` / `OLD_PROCESS_TIMEOUT`，程序文件保持原样；页面会离开「即将重启」。请只关闭画布主进程后再检查更新。安装路径中的目录链接会阻止替换；健康检查和回滚停止操作绑定本次启动的进程，避免误认或误停另一实例。安装或健康检查失败会还原程序、前端、Node 依赖和锁定的 Python 依赖，并尝试重新启动旧版。
- 本次备份位于 `%LOCALAPPDATA%\H3Workbench\updates\prepare-*\backup\`。确认新版稳定后可删除不再需要的旧 `prepare-*` 目录；更新状态为 `preparing` 或 `restarting` 时不要删除。
- 若自动恢复也失败，保留备份并重新运行 `install.bat`，不要删除项目目录或模型目录。更新接口不会要求管理员权限。

## 发布新版

1. 在同一个提交中更新 `package.json`、`package-lock.json` 的根版本和根包记录，以及 `workbench_lifecycle.py` 的 `APP_VERSION`。它们都必须与去掉 `v` 的 Release 标签一致，例如 `v1.1.0` 对应 `1.1.0`。
2. 在 GitHub Actions 手动运行 `.github/workflows/release.yml`。默认模式验证候选提交并上传 Actions artifact，可从候选分支运行，无需提前创建远端标签。检查测试、构建和六份候选文件。
3. 候选验收后，将该提交纳入默认分支并创建指向它的远端版本标签。正式发布由默认分支手动运行同一工作流，明确选择发布并提交完整 commit SHA。工作流核对远端标签与所提交的 SHA，向草稿上传三种 ZIP 及各自的 `.sha256`，核验远端六份资产成功后才公开 Release。已有草稿的发布说明会保留，已公开 Release 会被拒绝改写。
4. 确认 Release 公开且资产齐备后，再通知用户检查更新。更新从 GitHub `releases/latest` 发现正式版。普通提交、合并 PR、创建标签或仅运行候选校验都不会触发用户升级提示。

更新包由 Git 跟踪的公开程序文件生成；便携包另带本次构建的 `dist/`。Windows amd64 Python 运行时使用独立 ZIP。程序包排除本地项目、模型和密钥。GitHub 自动生成的 Source code ZIP 用于查看源码；用户安装和升级需要产品 ZIP 及其校验文件。

## 开发者验证

更新测试全部使用临时目录、合成 Release、合成 ZIP 和模拟进程，不访问真实 Release、不重启用户工作台、不读取模型或人物素材：

```bat
python -m unittest discover -s . -p "test_*update*.py" -t . -v
npm run build
node test-update-center-ui.mjs
```

覆盖版本比较、离线无打扰、标签绑定、令牌保护、活动状态阻止、恶意 ZIP、哈希不匹配、重复升级、用户目录保留、依赖失败回滚和界面重复点击。模拟 UI 测试不代表真实线上升级已执行；发布前仍应在另一台隔离测试机完成一次真实 Release 升级验收。
